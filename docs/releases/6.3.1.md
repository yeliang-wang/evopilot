# EvoPilot Runtime 6.3.1 — Token usage and bounded execution repairs

Status: **published and verified**. [Runtime v6.3.1](https://github.com/yeliang-wang/evopilot/releases/tag/v6.3.1), its six exact-version npm packages and GHCR image are public. The [publication ledger](../../governance/releases/runtime-6.3.1-publication-20261004.json) binds the actual public readbacks to the accepted Candidate. Acceptance, release authorization and publication remain separate records; [6.3.0](6.3.0.md) remains an immutable historical release.

## Changes

Native process observation v2 preserves reported input, output and cached input token counts without requiring monetary telemetry. Missing token telemetry stays unavailable; measured zero remains zero. Cached input is part of input, not an additional total. Original v1 receipts remain readable.

Runtime no longer estimates model prices or freezes, schedules or judges releases using monetary budgets. Historical externally supplied cost observations remain readable. Custom LLM profiles do not require pricing or a monetary cap. Token, time, source, scope, evidence, idempotency and authority checks remain in force. See [token usage and migration](../architecture/token-usage.md).

The bounded semantic evidence path now accommodates the existing default GA obligations: up to 31 collected observations and 32 total observations including Runtime process evidence. The previous limits of 15 and 16 could not represent all required GA evidence, outputs, Target and phase packages together. Collection and evaluation share one ceiling; byte, depth, node, scope, secrecy and replay guards remain. Regression tests retain the complete shipped phase criteria, evidence, review and output requirements and reject missing outputs and over-limit responses. Their synthetic observations do not establish real business acceptance.

Managed code upgrades can preserve an approved maintenance scope when a change includes documentation or governance files. Runtime previously inferred code roots and omitted those files, so a correctly constrained provider refused the complete change. The repair binds a finite exact file list to the owning accepted review, current project and source context, and proposal. Dispatch must reference that approval and reject stale or invalid scope before calling the provider. Explicit scope also requires the managed provider's declared capability and matching source-binding acknowledgment. Existing inferred behavior remains available when no explicit scope is supplied. Protected paths, tenant/workspace scope and publication authority remain enforced.

Semantic Target completion now readies eligible dependent Targets. A real default Goal journey exposed the earlier defect: a dependent successor remained `PENDING` after its predecessor completed. The semantic completion owner now verifies the predecessor Target receipt; crossing into the next phase also requires its verified phase receipt and GO decision. Advancement and completion use the same guarded Goal update. The original plan, Target definitions and evidence requirements remain unchanged. Readiness does not dispatch an Agent, complete another Target or authorize publication. See [semantic progression and recovery](../architecture/loop-runtime.md#semantic-target-progression-and-recovery).

## Compatibility and upgrade

Runtime 6.3.1 compatibility was verified with the unchanged, already published Evolution Expert 2.3.0 and evopilot-harness 4.8.1. Neither product needs a version bump or republication for this Runtime patch. Dashboard remains independently versioned; this patch does not publish a Dashboard or change its release ownership.

The acceptance installation also used independent local project extensions 1.0.1 for project validators, journals and the Codex executor. That private component has its own installation and qualification; it is not a public npm or GitHub Release supplied by Runtime 6.3.1. Project-specific source scope and business collectors still require configuration and qualification. A successful reference Goal does not configure every future project.

Before upgrading, preserve the installed product artifacts, configuration, credentials and daily Runtime data. Promote and verify the exact accepted release set rather than rebuilding it from a checkout. Reuse the configured LLM profile; repair or repeat preflight through supported APIs only if current readiness requires it. Do not import acceptance Goals, fixtures or receipts into a daily Runtime.

Read back durable pending requests and completion receipts before resuming interrupted work. Never redispatch an uncertain native request, and do not use the legacy Goal advance route to bypass a semantic-owned Target. Existing v1 usage receipts remain readable; consumers of v2 must accept absent monetary fields and unavailable token counts.

For recovery, use an explicitly recorded transaction bound to the retained product artifacts and current data. The acceptance campaign's historical rollback proof does not authorize replaying a transaction whose prerequisites have since changed. Separately authorized cleanup on the reference machine removed 76 legacy Suite roots containing 4,164 original files; that was local maintenance, not a Runtime uninstall or automatic deletion feature. The two non-Suite audit files from the additional failed-activation cleanup were retained. Release installation does not remove a user's Suites, credentials or journals. Retired Suites must never be used as a fallback execution path.

## Publication boundary

The user separately authorized publication after acceptance. The sealed local acceptance record correctly retains its earlier `publicReleasePublished: false` and `releaseAuthorized: false` values; publication is recorded by the later release authorization and promotion receipts, not by rewriting that record. A native GO decision, a successful test run or local Suite removal alone does not authorize a public release.

The completed publication promoted the accepted npm tarballs, image and accompanying assets without rebuilding and verified the public GitHub, npm and GHCR results.
