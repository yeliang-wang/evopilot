# EvoPilot v5.0.0 Release Notes

Status: **PUBLIC RELEASE — HISTORICAL BASELINE**

EvoPilot v5.0.0 is the published Harness-Guided Governed Evolution Runtime baseline. Publication and its historical aggregate acceptance are verified release facts, but they do not prove that every later-audited item in the original v5 design was implemented and validated criterion by criterion. That stricter closure belongs to v5.0.1 completion recovery.

## What changes

The product core remains Harness-guided Goal Target Loops. Every Loop must bind an exact eligible published immutable HarnessBundle, compose its obligations monotonically with an open Lifecycle, and revalidate the relevant Project, Harness, Lifecycle, policy, Host, Runtime, and evidence bindings before execution and resume.

Project-specific behavior moves into declarative, versioned Project Definitions and reference assets. DataRig, EvoPilot, `evopilot-harness`, and a new project demonstrate the model; none is a hard-coded Engine mode.

## User-visible capabilities

- Register, inspect, validate, adjust, and roll back declarative Project Definitions without adding repository-specific Engine branches.
- Explain Harness selection, abstention, immutable Bundle closure, Lifecycle composition, required evidence, conflicts, and authority boundaries.
- Collect typed parameters through the Runtime-owned Human Interaction Protocol and distinguish missing input from an actual human decision.
- Execute bounded deterministic recovery and use inspectable, scoped, revocable Automation Registry rules after their required one-time decision.
- Use Codex, WorkBuddy, generic Agent, MCP, CLI, API, or CI clients over the same Runtime protocol without giving any Host approval or release authority.
- Install the separately versioned Evolution Expert for guided onboarding, tutorials, documentation routing, progress explanation, recovery guidance, and release-readiness help.

## Runtime and Evolution Expert boundary

EvoPilot Runtime is version `5.0.0`. `@evopilot/evolution-expert` begins at version `1.0.0` and is not lockstep-versioned with Runtime. The Expert owns no canonical Project, Harness, Lifecycle, Goal, Target, Loop, evidence, recovery, approval, or release state; it renders and guides Runtime-owned protocol objects.

The two release units have independent Candidate artifacts, handoffs, acceptance records, release authorizations, tags, upgrades, rollbacks, and uninstall paths. Joint Host acceptance binds an explicit compatibility pair rather than merging the artifacts or authority boundaries.

## Historical Candidate construction

Candidate acceptance must start from private GitHub Actions artifacts built from one exact source commit:

- `.github/workflows/release-candidate.yml` creates the complete Runtime `5.0.0` release set and Runtime handoff.
- `.github/workflows/evolution-expert-release-candidate.yml` creates the Expert `1.0.0` npm tarball, SPDX SBOM, provenance, checksums, and Expert handoff.

Each workflow validates its own approved Target and version. Neither publishes npm packages, creates a GitHub Release, changes GHCR, operates a real Host, or authorizes Release. The exact Candidate sets must be freshly materialized outside the checkout before counted E2E.

## Compatibility and migration

The Expert package binds `@evopilot/contracts@5.0.0`; Candidate installation therefore uses the exact compatible Runtime Candidate dependency closure. Runtime remains fully operable through CLI, API, MCP, and CI when the Expert or a Host adapter is absent or incompatible.

Before v5 publication, the installed EvoPilot and DataRig Codex Suites remain active, untouched, and independently evolving. Candidate acceptance uses late-bound read-only snapshots for comparison and separate isolated environments where both legacy Suites are absent. Their actual disablement, archival, uninstall, default switch, or retirement is post-release work under a separate Cutover Target and separate explicit authorization.

## Historical validation contract

- `npm run check`
- `npm run release:ready`
- `npm run roadmap:release -- 5.0.0`
- `npm run evolution-expert:release:artifact`
- `npm run verify:evolution-expert-release-artifact`
- `npm run verify:release-pipeline`
- `git diff --check`

Repository validation is not Candidate acceptance. The later v5.0.1 completion
contract supersedes any inference that this aggregate alone covers the original
scheme: it requires criterion-specific evidence for one exact successor pair.

## Release and rollback

After complete acceptance, Runtime and Expert require their own exact release authorizations. Promotion must consume accepted bytes without rebuilding. Runtime rollback and Expert rollback are independent but must preserve their declared compatibility range and retained evidence.

This document records a completed historical release and grants no new
permissions. v5.0.1 Candidate construction, acceptance, publication, Suite
Cutover, or Release each remain separately governed.
