# EvoPilot v4.0.0 Release Notes

Status: **RELEASED**

EvoPilot v4.0.0 is the Open Lifecycle Harness release. The published GitHub Release assets, GHCR image, and six npm packages were promoted without rebuilding from the immutable Candidate that passed the complete Target acceptance set and received separate release authorization.

## What changes

EvoPilot v4.0.0 introduces an open Lifecycle Harness for executing a selected, immutable Harness asset against a project goal. A Lifecycle is a human-readable YAML resource with a versioned schema. It declares inputs, steps, conditions, evidence, retry and timeout limits, rollback behavior, risk policy, and the points where human authority is required.

The Engine remains deterministic and authoritative. CLI, API, CI, MCP, OpenCode, and other Agent integrations are adapters over the same Lifecycle contracts; they do not own approval, publication, project-release, or Harness-lifecycle authority.

## User-visible capabilities

- Interactive input collection replaces product-specific fixed parameters. Defaults, validation, secret references, and unanswered required fields are explicit.
- Decision policy minimizes repeated prompts. Low-risk deterministic steps may proceed automatically; declared risk, ambiguity, external side effects, and approval or publication boundaries remain human-controlled.
- Lifecycle definitions are open and extensible. DataRig internal-tool delivery and `evopilot-harness` open-source delivery are shipped as governed examples, not hard-coded product modes.
- The same plan and execution semantics are exposed through CLI, API, CI, local stdio MCP, and a public Agent runtime adapter contract.
- A first-class OpenCode adapter binds the exact adapter version, OpenCode runtime version, provider/model route, capabilities, workspace, time and output limits, and executor digest. It stores normalized evidence-only receipts and fails closed on profile, model, capability, or request reuse drift.
- An independent reference adapter is checked against the same public conformance suite to prevent the contract from becoming OpenCode-specific.
- v3 Alpha/Beta/RC/GA phase packages remain representable through the compatibility mapping, including preserved evidence and rollback semantics.

## Product boundary

EvoPilot owns project onboarding, published-Harness matching and binding, Lifecycle planning, goal-loop execution, project evidence, and project release decisions.

`evopilot-harness` remains the independent Harness producer. It owns Harness evidence ingestion, reasoning, authoring, evolution, review, approval, evaluation, Catalog/Registry, and publication. EvoPilot consumes published immutable Harness Bundles read-only and cannot publish or mutate them.

External Agent hosts operate EvoPilot through versioned adapters. Their conversation, model output, or host permissions never count as approval and cannot bypass Engine validation or digest-bound authority.

## Distribution

The published release set contains the existing EvoPilot packages plus:

- `@evopilot/adapter-mcp` for local stdio MCP operation;
- `@evopilot/adapter-opencode` for first-class OpenCode execution;
- Lifecycle JSON Schemas and example YAML resources;
- architecture, operating, migration, acceptance-matrix, and adapter documentation.

The public installers, npm packages, release archives, container, and chart resolve one consistent `4.0.0` product version. The release preserves the accepted Candidate bytes; it was not rebuilt during promotion.

Install the public CLI with `npm install -g @evopilot/cli@4.0.0`. The npm registry also contains `@evopilot/contracts`, `@evopilot/client`, `@evopilot/adapter-mcp`, `@evopilot/adapter-opencode`, and `create-evopilot` at `4.0.0`. The two adapter packages were published under the explicitly authorized v4.0.0 provenance exception; their registry integrity still matches the accepted tarballs.

## Migration

Existing v3 phase workflows are not silently reinterpreted. The compatibility layer maps their phase and evidence semantics into a declared Lifecycle, and rollback remains available. Teams may adopt the open YAML model incrementally while continuing to consume the same published Harness Bundles.

External Agent integrations should implement the public `EvoPilotLifecycleExecutorAdapterV1` contract. They must provide a fixed runtime profile, reject undeclared capability or digest drift, persist bounded normalized receipts, and keep credentials and raw model output out of acceptance artifacts.

## Acceptance completed

The immutable Candidate passed:

- AC01-AC18 from the approved `evopilot-v4.0.0-open-lifecycle-harness` Target;
- historical regressions HIST01-HIST05;
- RC01 DataRig lifecycle execution, RC02 designated-human WorkBuddy operation, RC03 Codex/CLI/API operation, and RC04 Harness producer-consumer boundary verification;
- OpenCode plus independent-adapter conformance for AC16;
- the AC18 functional, failure-recovery, performance, resource-limit, concurrency, isolation, cancellation, restart/recovery, security, observability, documentation, packaging, and active-soak matrix;
- the Target no-regression condition and release-readiness gates.

Implementation checks did not substitute for Candidate acceptance, and acceptance did not itself authorize publication. The retained Target and promotion records bind the completed release to its separate authorization, exact Candidate run, commit, handoff digest, acceptance digest, and public artifact identities.
