# EvoPilot v2.1.0 Release Notes

EvoPilot v2.1.0 turns the v2 domain HarnessTemplate model into an execution contract. The current domain scope is intentionally limited to database products and API gateway products.

## What Changed

- Upgraded `database-product-harness` and `api-gateway-harness` to `2.1.0`.
- Added `domainExecution.requiredActions` so generated `ProjectHarnessProfile` drafts say what the project owner must map before activation.
- Added `domainExecution.evidenceAdapters` so Beta, RC, and GA loops know which project evidence artifacts are required.
- Added `domainExecution.releaseBlockers` so domain-specific evidence gaps block release decisions instead of being treated as generic recommendations.
- Added repository module-boundary probes for database modules such as parser, planner, executor, storage, transaction, replication, and recovery, and gateway modules such as listener, route, upstream, policy, plugin, and protocol.
- Removed the enterprise-management public domain template from the v2.1.0 built-in/public template set.

## Database Product Boundary

`database-product-harness@2.1.0` is for the owner's self-developed database product. PostgreSQL, MySQL, SQLite, CockroachDB, TiDB, and similar systems remain compatibility corpora, dialect references, protocol references, or differential oracles. They are not the default product being evolved.

## API Gateway Product Boundary

`api-gateway-harness@2.1.0` is for gateway, ingress, traffic proxy, and service-mesh gateway products. Envoy, Kong, APISIX, Gateway API, and similar systems remain compatibility references or behavioral oracles unless the connected project explicitly owns that product.

## Compatibility

- Compatible Dashboard: `v2.1.0` for domain required actions, evidence adapters, release blockers, and repo-probe display.
- Compatible CLI/client/contracts packages: `2.1.0`.
- API contract version: `v1`.
- Node.js: 22 or later.
- Docker Compose: v2 for generated self-host stacks and ECS rollout.

## Install Paths

Install the CLI from the GitHub Release tarball set:

```bash
npm install -g \
  https://github.com/yeliang-wang/evopilot/releases/download/v2.1.0/evopilot-contracts-2.1.0.tgz \
  https://github.com/yeliang-wang/evopilot/releases/download/v2.1.0/evopilot-client-2.1.0.tgz \
  https://github.com/yeliang-wang/evopilot/releases/download/v2.1.0/evopilot-cli-2.1.0.tgz
```

Self-host bootstrap from the release tag:

```bash
curl -fsSL https://raw.githubusercontent.com/yeliang-wang/evopilot/v2.1.0/install.sh | bash -s -- --dir evopilot-stack
```

## Public npm Boundary

Public npm registry packages are a separate publication layer. After npm publication, verify the registry path:

```bash
npm run verify:npm-registry -- --version 2.1.0
```

## Validation

- `npm run build -w @evopilot/server`
- `npm run cli:test`
- `npm run check`
- `npm run release:artifact`
- `npm run verify:release-artifact`
- `git diff --check`

## Operator Notes

Normal project onboarding still uses automatic template matching. `--from-template` remains an administrator or advanced override. Generated domain profiles now surface required project actions, evidence adapters, release blockers, and repo-probe gaps in the DRAFT profile so the user or project owner can review them before activation.

Existing active `ProjectHarnessProfile` records are not silently rewritten. Projects that should move from a runtime/language template to a v2.1.0 domain template need a reviewed DRAFT profile and explicit activation.

## Rollback

Rollback to `v2.0.0` or the previous image digest, then verify `/health`, `/ready`, project harness template listing, profile generation, Dashboard compatibility, project usage endpoints, and release decisions.
