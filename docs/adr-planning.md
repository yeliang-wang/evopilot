# Project planning through EvoPilot

Status: accepted for isolated v0.7 implementation. Daily installation and shared maintenance remain deferred.

The Expert must support discussion before execution, using the same private project context across chats. Putting an entire conversation or Roadmap into an accepted ontology would mix proposed behavior, evidence and operational authority. Keeping the plan only in chat would lose revision identity and execution traceability.

Runtime therefore owns immutable planning revisions, exact decisions and execution bindings. The existing owner-local transactional record store provides receipts, revision conflicts and snapshot inclusion. Ontology continues to own domain semantics; Harness owns quality and acceptance rules. Neither a planning decision nor a conversation excerpt publishes either owner's assets. No new service or repository is introduced.

Expert records explicitly scoped excerpts, summaries or reference-only sources. Their categories remain distinct. Source material is data and cannot authorize commands. Speculative or rejected items remain visible in history. Approved planning describes intended future behavior, not proof of current implementation. Requirements link to native candidates; executable bindings resolve actual published owner references and the exact Runtime project, Goal and source baseline.

A new draft requires review before new dependent execution admission. Rejection preserves the previous accepted baseline. Accepting a replacement invalidates previous bindings; original claims and receipts remain available for reconciliation. Planning approval never authorizes collection, Run dispatch, semantic acceptance or software release.

All project records remain in the user's private Workspace. Repository Roadmap files are optional digest-bound exports, never a second writable authority. Export verification detects local edits; import is a separate future capability. The public product repository stores only generic implementation, documentation and synthetic fixtures.

Runtime schema 6 marks planning writes so older readers reject unsupported state. Historical native standards and contract bytes stay unchanged. Isolated upgrade, backup, restore, receipt replay and stale-binding rejection are required before deployment. A failed candidate is abandoned with its isolated state; the daily v0.6 environment is not modified.

References: [OpenSpec](https://github.com/Fission-AI/OpenSpec/blob/main/docs/overview.md) separates current specifications and proposed changes; [Spec Kit](https://github.com/github/spec-kit) separates specification, planning and implementation; [W3C PROV-O](https://www.w3.org/TR/prov-o/) informs source derivation. These are design references, not interoperability or complete PROV-O implementation claims.
