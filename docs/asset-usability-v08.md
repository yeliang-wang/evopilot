# v0.8 asset usability and controlled reconstruction plan

## Pre-v1.0 release scope

Before the v1.0 Release is published, Dashboard design, implementation, web UI, browser journeys and related acceptance obligations are excluded across all EvoPilot versions. Historical proposals do not authorize this work. After that release, any such work still requires a separately accepted plan; it does not start automatically. Standalone asset JSON APIs and Codex-readable reports remain in scope.


This document preserves the accepted **planning scope and acceptance requirements** for v0.8. The implementation is delivered in [v0.8.0 Preview](https://github.com/yeliang-wang/evopilot/releases/tag/v0.8.0); use the [current workflow](asset-usability-v08-workflow.md), [asset service](asset-service.md) and [delivery contract](asset-usability-v08-delivery.md) for operation. Historical `PLANNED_IMPLEMENTATION_DEFERRED`, `NOT_STARTED` and `NOT_EVALUATED` fields in the planning projection describe its authoring baseline, not current software availability. Publication does not certify a project's assets or establish completion of a later correction. Audience: product owners, implementers and reviewers of the four EvoPilot repositories. The [parent Roadmap](roadmap.md#v080-preview-asset-usability-and-controlled-reconstruction) owns EVO-F06; the [planning record](../governance/asset-usability-v08.json) preserves the same IDs and mappings for machine inspection.

## Objective and prerequisites

Deliver independently consumable Ontology assets, explicit L1/L2/L3 usability claims and a controlled reconstruction workflow that verifies a real functional slice. v0.7 provides the accepted readable-query, comparison, diagnostic and presentation foundation. Planning can proceed while v0.7 evolves; dependent implementation must bind its actual accepted contracts and candidate identity. This plan neither changes v0.7 scope/status nor resumes it. Existing project work continues independently.

Reuse native RDF/Turtle, bounded SHACL/pySHACL, Rego/OPA/Conftest, source bindings, immutable publication and existing owner services. Start with an asset-consumption experiment and a gap inventory, then improve content, queries or execution as evidence requires. Do not assume the ontology core or a project's whole model must be rebuilt. A limited functional slice is mandatory; universal reconstruction, source-code identity and binary reproducibility are not the product promise.

## Levels and public promises

These levels are EvoPilot conventions. Level means supported use within a declared scope, not graph granularity, document length, source-file count, model-test count or a percentage score. Higher levels include lower-level requirements for the same scope.

| Level | Public promise | Required content and evidence | Suitable uses |
|---|---|---|---|
| L1 — Understanding / low | The assets explain the declared domain and support informed software prototyping. | Exact identity/scope/source, defined concepts and relationships, important constraints, assumptions and known gaps; independent readers can answer the frozen domain questions with traceable answers. | Discovery, onboarding, project Q&A, handover, requirements discussion and prototypes. |
| L2 — Implementation specification / medium | The assets specify the declared functions sufficiently for an independent implementer; implementation still needs acceptance. | L1 plus normative inputs/outputs, interfaces, state transitions, pre/postconditions, errors, side effects, applicable idempotency/concurrency/recovery rules, dependency/environment constraints and acceptance mappings. Every mandatory behavior has a reviewed disposition; no required unresolved business interpretation. | Module implementation, scoped rewrites, adapters, alternative implementations and version evolution. |
| L3 — Reconstruction verified / high | The exact asset set has supported independent specification-driven reconstruction, with functional equivalence verified under the declared conditions. | L2 plus isolated reconstruction receipts, independent behavioral oracles, two clean reconstruction attempts, complete mandatory results, reproducible environment/tool identities and explicit limitations. | Verified module replacement, bounded legacy reconstruction, platform migration and supplier substitution in the assessed scope. |

An asset set includes the ontology and exact references to related behavior/interface specifications, fixtures and environment descriptions. They need not all be RDF. Each fact has a declared authority and mapping; generated schema, code or prose is a projection, never a silently introduced second editable source of truth. Referenced specifications must be available to the consumer with an explicit license/access disposition. Unsupported mappings, semantic loss and inaccessible required dependencies block the affected claim. New vocabulary/profile needs must be established by the pilot rather than presumed.

### Claim identity and state

The additive assessment contract must bind at least: assessment standard/version/digest; Workspace/project and visibility; exact asset references/digests; declared source baseline; functional scope and exclusions; target level; verified level or null; assessment status; required-requirement inventory/digest; equivalence profile/oracle digest; environment and allowed dependency pins; consumer input-manifest digest; evidence and review references; assessor identity and independence; assessment time and freshness/revalidation disposition. Runtime evidence additionally binds executor/Agent/model/tool/configuration identities, attempts, cost/token information when available, human interventions and output artifacts. Unavailable measurements remain unavailable, not zero.

Keep assessment state separate from asset lifecycle, execution status and approval. Planned assessment states are `NOT_EVALUATED`, `IN_PROGRESS`, `VERIFIED`, `FAILED`, `INCOMPLETE`, `STALE` and `UNSUPPORTED`; requesting L3 never sets `verifiedLevel` to L3. A failed higher-level attempt does not erase valid historical lower-level evidence, and a lower-level fallback must name the exact still-valid scope/evidence. Display failures and the target-level gap alongside it. Old assessments remain immutable and readable.

Claims apply to a versioned functional slice, not automatically to its whole project. A project-wide level requires every included mandatory slice and their integration obligations to meet that level. Never average levels, replace a failed slice with a smaller denominator, or hide failures using a display filter. Review legitimate scope changes as new scope/assessment identities. Functional equivalence does not imply identical UI, performance, deployment behavior, source or binaries; each additional guarantee needs its own declared profile and evidence.

## Modeling purpose and mandatory admission

L1/L2/L3 are cumulative content and evidence profiles, not three incompatible ontology formats or graph-size grades. Authoring templates collect the relevant definitions, normative behavior and reconstruction configuration. Completing a template does not assign a verified level. L3 additionally requires actual independent clean reconstructions and independent acceptance; reverse extraction alone cannot verify it.

Before formal reverse modeling, Expert first resolves the user's purpose and functional scope, then recommends a target level and explains cost, obligations and exclusions. Reuse explicit, unambiguous conversation or retained project intent; ask only about missing or materially ambiguous information. Read-only source discovery and reading/importing an existing published package for consumption do not require a new modeling decision or assessment.

Formal reverse candidate creation requires a durable, exact intent binding containing purpose, Workspace/project/source identity, functional scope and exclusions, target L1/L2/L3, the independently fixed mandatory requirement/acceptance inventory and traceable actual user intent. Requirements are determined before generating assets and cannot be narrowed to match current extraction coverage. An explicit empty exclusions list is allowed; an omitted scope or unresolved mandatory interpretation is not.

Enforce admission in the owning service paths used by Expert, MCP, HTTP and SDK, not only in conversation instructions. Missing, conflicting, stale, inaccessible or tampered intent returns a typed blocker before candidate/asset writes. Caller-supplied approval flags, a template name, a requested level or an Agent statement cannot substitute for the retained binding. An already clear intent does not require another conversation confirmation. Changing source, purpose, scope, exclusions, target or mandatory inventory requires a new reviewed binding; preserve prior candidates, decisions and assets.

New reverse preparation, freeze/materialization and owner authoring paths must not provide alternate admission routes. Historical records remain readable and exact completed-operation readback remains available; unfinished legacy modeling must obtain a current intent binding before new modeling writes. This is an additive versioned admission contract; frozen native-v1 bytes and historical evidence are not rewritten. A compatibility-impact assessment and executable bypass checks precede rollout.

Template selection sets only the target. Harness assesses the actual level from independently owned evidence; Runtime retains execution identity and completion decisions. Show target, verified level or null, status, scope and gaps separately. Per-slice levels cannot be averaged into a project-wide claim. Intent admission grants neither a domain-model approval, collection/Run decision, asset publication nor software release.

Bind this refinement to V08-R04/R05/R07/R14 and V08-E04/E05/E07/E15, with V08-E18 compatibility and V08-E20 complete traceability. Preserve all 18 requirements, 20 acceptance IDs, two clean reconstructions and the successful real pilot/evolution. Required E2E variants cover each missing field, ambiguous intent, reuse without repetitive prompting, L1/L2/L3 profile selection without grading, changed bindings, direct service/SDK and transport bypass, old records, read-only consumption and independent target/verified presentation. Installed Expert journeys remain required separately from source tests.

The service must support an independent consumer without a Runtime business project/Goal/Run or Codex session activation as a prerequisite for read access. Owner initialization and authenticated service configuration remain explicit. Reading assets never dispatches business work, approves a model or publishes an asset. The current conversation-activation contract remains intact for existing Codex mutation paths.

Provide documented, versioned list/discover, exact readback, entity/relationship/constraint/source-mapping queries and export operations through a bounded authenticated HTTP profile and the existing owning SDK. Freeze exact routes, schemas, pagination/snapshot behavior, errors, payload/time/resource limits and compatibility before implementation. Support requested-version discovery, but resolve and return immutable pins before consumption; no implicit latest-version replacement in an assessment or Run. Retain an offline export path and prove that downloaded bytes and allowed dependencies match the selected input manifest.

Authentication at the transport and authorization at the owning boundary must enforce Workspace/project/visibility scopes, distinct read/mutation rights, credential revocation and audit. Configure credential references privately; do not bundle credentials in assets or expose them in URLs/reports. Default to local binding; any non-loopback service selection requires explicit configuration, TLS and equivalent authorization checks. A real bounded non-loopback consumer path must be exercised in isolation if that transport is delivered. This is a self-hosted consumption interface, not a new managed cloud registry, graph database or default internet deployment. Rate/output bounds, missing dependencies, stale cursors, tampered packages and partial exports must fail explicitly.

Exact original deliveries remain readable under their existing access controls. Consumer-facing specification projections carry their own digest and provenance back to the original asset; redaction or excluding source files must never be mislabeled as the original package or inherit its approval automatically. Validate the projection and include its exact identity in assessment. Source text, links and annotations are untrusted data, not instructions or executable authority.

## Reconstruction protocol

1. **Freeze the question.** Select a privately authorized real-project functional slice, source baseline, requirements, environmental/quality profile, interfaces, observable behavior and exclusions before generating implementation. Establish the required inventory independently of what the existing ontology happens to contain. Record intentional corrections to original bugs as explicit contract changes; compare against the approved contract rather than silently copying or changing defects.
2. **Inspect assets and close gaps.** Reuse existing exact deliveries; classify findings as asset-content gaps, query/presentation gaps, unsupported representation, provider limitations or implementation defects. Supplement project assets through new reviewed versions. Missing mandatory semantics, unavailable dependencies or unsupported execution must remain blockers. Pilot lessons may justify a bounded product change under the execution Target, not a wholesale rewrite by default.
3. **Separate consumer and auditor inputs.** In `SPECIFICATION_ONLY` mode the builder sees only the reviewed specification projection, declared generic dependencies and permitted fixtures. Original source snapshots, executable reference binaries, prior generated solutions, hidden oracle outputs and services that delegate the target behavior to the original implementation are excluded. The evaluator may separately access the frozen reference implementation. References cannot grant the builder access to denied material through paths, network endpoints, symlinks or cached files. `SOURCE_ASSISTED` mode is recorded separately and cannot substitute for this plan's L3 proof.
4. **Execute through a supported adapter.** Bind actual Agent/executor/model versions or returned identifiers, prompts/configuration, allowlisted tools/network/filesystem, dependency locks, artifact digests, human interventions and time/token/cost/iteration budgets. Retain generated implementation and actual build/test receipts. The execution Target must prove the selected adapter's installed entry, real build/run and interruption/recovery before the real pilot. Existing Node collection or Host access does not imply Java/Maven or coding-Agent support. Any pilot-required adapter is a bounded RUN-F01 prerequisite within RUN-F06's reviewed Target, not an excuse to substitute synthetic results or create a general CI engine. Controlled iterations operate within the reviewed plan; this is not autonomous selection of unrelated Goals or an unlimited repair loop.
5. **Evaluate independently.** Harness owns the frozen oracle and independent acceptance set; the implementation generator cannot replace them with its own tests. Use differential/reference behavior and normative contract assertions as appropriate; compare outputs, state transitions, errors and external side effects. Define allowed nondeterminism, ordering, random seeds/distributions, timestamps, numerical tolerances and environment differences before running. Include normal, negative, boundary, concurrent and recovery scenarios when applicable; non-applicable cases need prior reviewed reasons. Verify oracle effectiveness with deliberately faulty implementations, including incorrect replay/idempotency and false-completion behavior. Include acceptance checks withheld from the generation/fix loop and retain their independent provenance.
6. **Repeat cleanly.** Require at least two independent empty-workspace reconstruction attempts using the same frozen specification input. Do not reuse a generated solution between attempts; both must pass all mandatory cases. Record failed attempts and interventions instead of selecting only a successful run. At least one consumer operates independently of the asset/oracle author with no original implementation context. Two models or platforms are not universally required; a cross-Agent/platform claim requires its own multi-Agent/platform matrix. Pinned LLM settings improve traceability but do not establish deterministic code generation.
7. **Test evolution.** Introduce one substantive, reviewed change to the selected asset contract; create a new version and assess its impact. Preserve previous assets and results. The updated reconstruction must pass the new requirements and retained compatibility obligations, or an explicitly approved migration contract. Changed asset/scope/oracle/dependency/environment identities invalidate current reuse unless a review proves the declared compatibility rule permits it. Never transfer L3 automatically to the next version.
8. **Close honestly.** A real passing pilot and its evolved version are required for V08-T5. Correct failure reporting is necessary product behavior but cannot satisfy the positive pilot requirement. Missing, failed, skipped, unknown, stale, synthetic-only or unsupported mandatory evidence blocks verified L3 and plan completion. Exhausted budgets retain a failed/incomplete assessment. Any change to the scope or gate requires explicit review and fresh bindings; it cannot backdate success.

Finite tests support a bounded engineering equivalence claim, not a proof of equivalence for every possible input. Report the evaluated conditions and limitations prominently. L1/L2 users can consume assets without undertaking reconstruction; using the service does not require a level assessment or an L3 workflow.

## Reference basis

- [LCIM](https://arxiv.org/abs/0908.0191) distinguishes technical through conceptual interoperability; it is not a software reconstruction certificate.
- [OMG MDA](https://www.omg.org/mda/specs.htm) separates platform-independent behavior from implementation mappings; its modeling views are not these three grades.
- [ISO/IEC 25010:2023](https://www.iso.org/standard/78176.html) informs explicit software quality/acceptance profiles; no ISO certification is claimed.
- [Semantic-artefact catalogue maturity research](https://arxiv.org/abs/2305.06746) informs service governance and availability, not behavioral equivalence.
- [SHACL](https://www.w3.org/TR/shacl/) establishes graph constraint semantics, not software behavior. [LinkML generators](https://linkml.io/linkml/generators/index.html) and [OBA](https://github.com/KnowledgeCaptureAndDiscovery/OBA) are possible bounded-generation references, not mandatory dependencies or proof that the adopted RDF subset maps losslessly.

## Versioned composed execution authority

[ADR 0011](architecture/0011-controlled-process-authority.md) governs the accepted bounded correction for composed projects.
