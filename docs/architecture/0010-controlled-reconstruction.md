# Controlled reconstruction execution

Runtime owns an additive `reconstruction.*` API, durable attempt claims, cancellation and execution receipts. Harness continues to own independently frozen behavior oracles and their verdicts. An execution success does not award L3, complete a project or authorize release.

A reconstruction plan binds an accepted Runtime planning revision and milestone, exact inventory/specification/oracle/input/environment/dependency digests, executor identity, origin, input mode, independent consumer declaration and cumulative budgets. Freeze requires a decision for that exact plan. Installation-owned providers must recheck the authoritative assets and pins before execution and before evidence consumption. JSON requests cannot register providers, supply observations, execute commands or claim PASS. A changed planning head or missing decision blocks new dispatch and current evidence while preserving history.

### Execution limits and recovery policy

There is no universal industry duration for software reconstruction. Select a plan's deadline from observed generation/build/run latency, expected network delay and cleanup headroom. The current configurable ceiling is 3600000 ms (60 minutes) per plan; it is an EvoPilot engineering bound, not an industry certification or an equivalence criterion. Existing frozen plans retain their lower deadlines. A larger supported ceiling never replenishes an exhausted plan or turns unknown token usage into zero.

Follow [AWS timeout and retry guidance](https://aws.amazon.com/builders-library/timeouts-retries-and-backoff-with-jitter/) and [bounded inference retry guidance](https://docs.aws.amazon.com/bedrock/latest/userguide/scaling-throughput-best-practices.html): retry only transient errors that are safe to repeat, use bounded backoff with jitter at the transport layer, and avoid multiplying retries across layers. The pinned Codex client owns its transport reconnections; EvoPilot records its events and does not claim to configure or certify that client's backoff algorithm. Runtime never adds blind generation retries. An unknown result must reconcile its original claim. A terminal failure can be followed by a separately authorized bounded recovery plan, preserving the original result, usage uncertainty and complete history.

Execution deadlines protect resources. Semantic approval, fixed oracle cases, two independent successful reconstructions and release gates determine acceptance. A timeout leaves those gates incomplete while independent diagnosis and authorized preparation can continue. No timeout or retry policy waives a required case or establishes L3.

Runtime persists the claim before external execution. One unresolved builder blocks additional dispatch across all scopes. Each plan permits two to four attempts; the limit includes failures. Tokens, cost and wall time are cumulative. Each attempt retains its ordinal and remaining budget. Exact request replay returns the original admission and current attempt without redispatch. Timeout, unavailable receipts and invalid receipts remain UNKNOWN until the original adapter supplies a verified terminal receipt. Cancellation remains sticky. Late callbacks cannot replace an already reconciled terminal outcome. Reconciliation never executes a builder.

The state marker advances to 7 on reconstruction writes. Existing v0.7 writers reject it. Recovery uses the existing stopped workspace backup and relocation interfaces; historical claims and receipts keep their identity. Opening or reading does not itself migrate the marker.

## Supported local adapter boundary

`integration/usability/local-reconstruction.ts` supplies the first bounded offline process adapter. Its supported environment is macOS with Node 24.14.0 and Seatbelt. Executor, driver files, input manifest, OS/runtime identity and stage configuration are pinned. It supports a local offline generator with provider `local-offline`, model `none`, zero token/cost budgets and one generation iteration. It does not claim support for an authenticated coding Agent or a remote model. Those require a separately validated adapter and actual usage receipts.

The generator receives a declarative specification projection. It emits a bounded JSON file bundle on stdout; the trusted worker materializes regular files. Builder processes have no filesystem write permission, network access, process-fork permission or IPC delegation permission. Content reads are limited to pinned drivers, specification, that attempt's workspace, and system runtime libraries. Root-directory listing and read-only file metadata are allowed for the Node loader; this is not a promise to hide host path names. No ambient HOME, credential environment, package cache or previous attempt output is inherited. The worker, request journal, oracle and original source are outside the process read allowlist.

Generation, module build and execution are separate real processes. Each stage has a deadline and bounded output. The worker persists stage process records and a terminal receipt outside the builder sandbox. A parent interruption can inspect the original worker journal. If a worker dies before retaining a receipt, Runtime keeps UNKNOWN; it does not retry. Successful receipts are revalidated against current output bytes before Harness may consume an observation.

The offline adapter consumes an independently reviewed specification-only projection from its trusted resolver. File extensions and process isolation alone do not establish semantic independence of a supplied generator or input. The plan and owner review must establish that original implementations and hidden oracle material were not embedded in those inputs or drivers.

## Authenticated Codex admission

The selected Codex route needs its own installed-executable and native permission-profile verification. A fresh working directory and the legacy `workspace-write` setting alone do not establish source isolation. Require a restricted read allowlist, a separate writable attempt directory, denied command networking, disabled external tools/hooks/delegation, and actual negative probes for original source, withheld oracle, previous outputs, credentials, symlinks and outside writes. Authentication stays in the trusted Codex host; it must remain unreadable to generated commands. Record the exact executable, model/provider, configuration, system dependency paths and model-visible instruction sources. Automatically loaded global instructions and skills must be excluded or independently reviewed and digest-pinned as generic build policy; they cannot silently carry project knowledge into an assets-only attempt.

The trusted adapter must retain the original claim, executor process identity, Codex thread/turn identifiers, event journal, output digests and usage. Test both controller loss with a surviving worker and executor loss after an observable effect. A read-only `thread/read` from a different app-server is advisory: a live thread can appear unloaded or interrupted there. It is not a verified terminal execution receipt. Reconciliation combines the original worker journal and process disposition with exact retained Codex events, without starting another turn, resuming generation or rerunning a command. A terminal model response also does not prove the generated program's build or behavior.

Keep missing usage measurements explicit. A ChatGPT-authenticated run can return token totals without a monetary charge measurement; that missing value is not zero. Interrupted generation may lack final token totals as well. The current offline adapter's numeric zero-cost receipts cannot be reused for this route. Before Runtime admits the authenticated adapter, its receipt/budget contract must represent unavailable measurements and block any budget claim it cannot establish. Capability probes with synthetic tasks do not register a production adapter, certify independent project reconstruction, or close fixed release acceptance variants.

The candidate `codex-structured-node-v1` adapter pins the installed Codex 0.163.0-alpha.10.2 executable and its effective configuration. Its trusted App Server uses the existing host authentication reference, generates a bounded JSON file bundle with tools disabled, and retains the original thread/turn IDs. Configuration and model-visible generic policy pins are checked before inference. Undeclared instructions, active MCP tools, permission drift or unexpected tool execution reject admission. The current profile accepts the default host configuration location only; it does not copy authentication into a reconstruction workspace.

The trusted worker materializes generated regular files, then imports and runs them in separate read-only Seatbelt processes with no network, child-process or host-credential access. `networkDenied` describes generated-code authority; the trusted authentication broker still contacts the explicitly selected model provider. The adapter supports flat Node ES module bundles, not arbitrary package installation or deployment. Known token totals are cumulative; monetary cost stays null under an explicit null ceiling. A missing final token measurement prevents another attempt under that plan. These limits are checked at admission and against retained completion evidence; they do not promise a provider-side hard token cutoff before its next usage event.

## Bounded persistent state

`codex-structured-node-state-v1` adds an explicit `state: {kind: 'fixed-hfs-v1', bytes: 8388608}` input. The other supported fixed capacity is 67108864 bytes (64 MiB). Its configuration, environment and dependency digests differ from the read-only adapter; existing read-only inputs keep their digests. Storage tools are fixed system executables with pinned bytes. This profile allocates one fixed case-sensitive HFS image per attempt. Filesystem metadata reduces usable capacity. State storage has a separate fixed bound from the plan's generated-output and stream limits.

Only the mounted state directory, passed as `EVOPILOT_STATE_DIR`, permits writes by generated code. Generated modules and declared drivers remain read-only; the journal, disk-image file, original sources, withheld oracle and host credentials remain outside the allowlist. Build and run are separate processes sharing that attempt's volume. A second attempt receives a fresh volume. SQLite is available through the pinned Node runtime; package installation, networking and child processes remain unavailable.

A trusted phase supervisor owns the volume and stage processes. It retains create, attach and detach intents and checks the current exact image/mount/device association before detaching. It never detaches a device merely because a stale journal mentions its number. Cancellation or worker-pipe loss kills the active stage and closes the volume. A terminal reconstruction receipt is written only after verified cleanup. The retained trace includes storage metadata, the detached image digest and stage results; later image mutation invalidates readback.

An optional `state.seeds` list declares two to four private evaluation-input images, each with `{image: {path, digest}, mountPoint}`. Every slot has a distinct reserved empty private mount directory, disjoint from the attempt's control directory; the plan's attempt limit cannot exceed the slot count. The ordinal selects one slot without fallback. The worker verifies and copies the immutable image into its own directory and mounts only that copy. Occupied or already mounted paths, source-image drift and conflicting device identities fail closed. Seed images are not edited. Their exact data and paths are part of the plan configuration; the generation prompt includes only capacity and environment, withholding seed locations and metadata.

Seeded data is an explicitly reviewed test input, never an original implementation, a prior reconstruction output or a hidden expected answer. Reference software may prepare synthetic initial state outside the generated sandbox. Its code must not appear in the image or readable drivers. The independent review must establish this semantic boundary; a matching disk-image hash alone cannot do so. Each attempt still starts in a fresh execution directory with its own copied input volume. Readback rechecks the original seed pins as well as the retained result image and never remounts either image.

A stateful input may pin a standalone `stages.observe` driver. After generated build/run processes exit, this separate process can read the state volume, its own driver and system runtime libraries; it cannot write state or read generated modules and other drivers. It captures bounded observations under the same remaining deadline and cumulative stream limit. The trusted driver must treat files as data and contain no hidden expected outcomes or original implementation. Its protected process record and output join the execution trace. Harness compares retained observations outside the generated program; reconciliation only reads them and never starts the observer again.

Failed or uncertain mounting, supervisor loss and cleanup failure cannot be converted into success or a fabricated failed receipt. They retain UNKNOWN and the Runtime execution lock for exact recovery; reconciliation never mounts, reruns or retries. If the supervisor itself is killed, automatic cleanup is not established: preserved identity evidence is required for maintenance. Worker loss can leave a closed volume and phase result without the original complete receipt; that also remains UNKNOWN. Reported wall time includes actual cleanup time without truncation, and an overrun cannot satisfy success or reset the remaining budget.

One narrowly identified pre-release defect has an explicit stopped-execution recovery: the old state CLI rejected a deadline above 600000 ms before reading the request or preparing storage. `recoverCodexStateAdmission` accepts only the exact reviewed legacy module bytes, that precise rejection site, matching completed generation journals and output, an original worker UNKNOWN journal, absent worker/generator/phase processes, no storage or stage evidence, and no owned mounted image. PID reuse, incomplete evidence, a different crash or any state effect rejects recovery. It does not execute generated code, mount a volume or dispatch generation.

This maintenance path writes a separate `recovery/evidence.json` and failed-only `recovery/receipt.json`; it never invents the original worker receipt or edits original files. Runtime consumes it through the same trusted adapter and original claim reconciliation. Generation tokens come from the retained turn events; unknown cost stays null. Wall time runs from original admission through verified recovery closure, including the unresolved interval, and cannot replenish the exhausted plan. The receipt identifies its forensic recovery provenance and has no successful build/run, accepted output, L3 or release authority. Ordinary worker/supervisor loss continues to retain UNKNOWN. T4-C19/C20 supplement the fixed acceptance with actual legacy-process reproduction and negative recovery cases; their model transport and maintenance clock are explicitly synthetic.

## Remaining release evidence

Synthetic specifications and actual sandbox processes demonstrate mechanics only. The v0.8 release still requires the actual supported reconstruction route, independently reviewed real project specifications and oracle, two independent real reconstructions, version evolution, actual Host journeys and the remaining fixed acceptance variants. Missing evidence remains missing. No graphical frontend work is included before v1.0 release.

## Accepted composed-profile correction

[ADR 0011](0011-controlled-process-authority.md) supersedes the blanket offline/process restriction only for explicitly reviewed v2 profiles. It preserves this document’s v1 adapter semantics and historical evidence. An enabled owned-process loopback profile reports network denial accurately through its versioned policy and enforcement receipt; it cannot be presented as an offline v1 run.
