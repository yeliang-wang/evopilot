# Local process topology

The v0.6.0 candidate retains the bounded local connection foundation around the public Runtime, Harness and Ontology composition. This source implementation does not establish Host acceptance or release authority. Current acceptance follows the [v0.6 Target](../../governance/response-v06.json); historical M3 and E01–E19 results do not certify a new installation.

Codex starts a separate stdio adapter for each conversation. Its activation explicitly starts or reuses a shared detached loopback process for the canonical workspace. The current installer and adapter use the exported connection API. The daemon loads the three public installed packages through `loadInstalledProducts`, initializes Runtime on activation, and initializes Harness/Ontology only on explicit owning operations. Each product protects its own transactions and locks. The parent distributes compatibility material and has no business state. Imports, configuration loading and passive connection inspection perform no initialization or writes.

The explicitly configured [online worker](0005-online-harness.md) is a separate supervised process. Chat deactivation does not stop it. Both the worker and the shared connection must be stopped for consistent maintenance. Runtime response actions use the existing isolated collection worker; no new general-purpose production remediation daemon is supplied.

An external closed configuration binds the executing parent installation, its executable content manifest, component versions, and canonical workspace identity. A private sibling control directory coordinates all installations targeting that workspace. The daemon wins an atomic startup election before product initialization, listens only on numeric loopback, and authenticates every request with a private token plus exact public identity/nonce. Clients forward existing composition operations once. Client exit leaves the shared process alive; authenticated stop refuses in-flight work. Stale recovery is explicit and requires exact metadata and proven process death. See [local service API and manifest contract](../local-service.md) for exports, limits, errors, and verification commands.

Readiness must bind the exact product identity, version and canonical workspace path before reuse. Private authentication material must never appear in health responses. Startup failures must be bounded and actionable; an unknown PID must never be killed. Diagnose stale locks using ownership and process evidence instead of deleting them blindly. After an uncertain response, read the retained receipt before any retry; uncertainty does not authorize redispatch.

M0 evidence includes distinct MCP processes in two real Codex conversations, read-only inspection followed by explicit activation, zero product operations, shared-service concurrency, receipt and restart checks, and detached starter exit. A portable contract was exercised by two consumers under Node permissions denying original source reads. An offline three-submodule clone was verified. These feasibility results are not release authority or final product E2E completion.
